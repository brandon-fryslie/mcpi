## Critical Decision Points (MUST CLARIFY)

### 1. Tier 3 Server Validation Scope

**The Question**: Should Tier 3 validate ALL catalog servers or a reference set?

**Context**:
- Proposal says "For each cataloged server" but catalog has 50+ servers
- At 5-10 min per server, that's 4-8 hours of test time
- Many servers require external services (GitHub API, databases, etc.)
- Some servers may be unmaintained and broken

**Options**:

**Option A: Reference Set (5-10 "known good" servers)**
- Pros: Fast (30-60 min), maintainable, catches MCPI bugs
- Cons: Doesn't validate full catalog quality
- Examples: filesystem, memory, postgres (if docker), github (if mock API)

**Option B: Full Catalog**
- Pros: Validates entire catalog, catches broken servers
- Cons: Slow (4-8 hours), needs extensive mocking, high maintenance
- Requires: Strategy for servers needing external services

**Option C: Tiered Catalog Validation**
- Pros: Best of both - fast core set + weekly full validation
- Cons: More complex setup
- Structure: Core 5 servers (15 min) on every Tier 3 run, full catalog (4+ hours) weekly only

**Recommendation Needed**: Which approach aligns with project goals?

### 2. Windows Docker Strategy

**The Question**: How do we handle Windows testing?

**Context**:
- Current CI tests on Windows via GitHub Actions (no Docker)
- Docker Desktop on Windows has licensing and complexity issues
- Windows users are significant user base
- Real file path differences (C:\Users vs /home)

**Options**:

**Option A: Skip Docker on Windows, rely on Tier 1 integration tests**
- Pros: Simple, no Docker complexity
- Cons: Less coverage on Windows-specific issues

**Option B: Use WSL2 in GitHub Actions for Docker**
- Pros: Docker works in WSL2
- Cons: Another abstraction layer, potential path issues

**Option C: Windows-native tests without Docker**
- Pros: Tests real Windows environment
- Cons: Duplicate test maintenance

**Recommendation Needed**: What's acceptable coverage vs. maintenance tradeoff?

### 3. Test Authentication Strategy

**The Question**: How do we test servers requiring API keys?

**Context**:
- Many servers need auth (GitHub, Slack, databases)
- Can't use real API keys in CI
- Mock APIs are complex to set up
- Tests without real auth miss a whole class of bugs

**Options**:

**Option A: Mock API responses**
- Pros: No real credentials needed
- Cons: Doesn't test actual API integration, high maintenance

**Option B: Use test/sandbox APIs where available**
- Pros: Real integration testing
- Cons: Not all services have sandbox, rate limiting issues

**Option C: Skip auth-required servers in Tier 3**
- Pros: Simple, focuses on MCPI functionality
- Cons: Significant catalog coverage gap

**Option D: Hybrid - local servers (filesystem) fully tested, API servers lightly tested**
- Pros: Pragmatic balance
- Cons: Partial coverage

**Recommendation Needed**: What level of authentication testing is required?

## Implementation Red Flags

### 1. No "Test the Tests" Phase

**Issue**: Proposal jumps to adding e2e tests without validating current test quality.

**Evidence from code review**:
```python
# src/mcpi/installer/npm.py:252
if self.dry_run:
    return subprocess.CompletedProcess(
        args=["npm"] + args,
        returncode=0,  # Always returns success!
        stdout=f"[DRY RUN] Would execute: npm {' '.join(args)}",
        stderr="",
    )
```

All current installer tests use dry_run=True, which means:
- Tests never verify npm actually works
- Tests never catch installation failures
- Tests can't detect version conflicts
- Tests miss all real-world npm issues

**What's needed**: Before writing e2e tests, verify current tests catch real bugs:

1. Introduce a deliberate bug in NPMInstaller (e.g., wrong npm command)
2. Run test suite
3. If tests still pass, current tests are worthless for that code path

**Recommendation**: Add Phase 0 before Phase 1:
- Phase 0: Test Quality Audit
  - Try breaking installers - do tests catch it?
  - Try breaking scope handlers - do tests catch it?
  - Try breaking catalog parsing - do tests catch it?
  - Document which tests are real vs. theater
  - Fix or mark as known gaps

### 2. Container State Management Unclear

**Issue**: Proposal doesn't specify how to prevent test pollution in Docker.

**Example scenario**:
1. Test A installs filesystem MCP server globally in container
2. Test A fails before cleanup
3. Test B runs and assumes clean state
4. Test B's "install" test fails because package already exists

**Missing from proposal**:
- Per-test container snapshots or cleanup strategy
- Decision on global vs. local npm installs in tests
- Cleanup of ~/.cache, ~/.npm, ~/.local between tests

**Recommendation**: Add explicit container lifecycle management section to proposal.

### 3. Flakiness Risks Underestimated

**Issue**: Proposal acknowledges flakiness but doesn't have mitigation strategy.

**Sources of flakiness**:
- Network issues downloading npm packages
- npm registry rate limiting
- PyPI temporary outages
- GitHub API rate limits (for git-based servers)
- Timing issues in MCP protocol handshake
- Port conflicts if multiple servers start

**Proposal says**: "Cache npm/pip packages, retry logic"

**But doesn't specify**:
- How to cache packages (volume? committed to repo?)
- Retry strategy (how many times? exponential backoff?)
- Timeout values (5 sec? 30 sec? per-test? per-suite?)
- How to distinguish real failure from flaky failure

**Recommendation**: Add explicit reliability requirements:
- Target: <1% flakiness (proposal says this but no strategy)
- Strategy: Pre-cache all Tier 3 validated servers in Docker image
- Timeouts: Specify for each operation type
- Retry logic: 3 attempts with exponential backoff for network operations
- Failure isolation: Mark tests as flaky vs. real failure

### 4. MCP Protocol Testing Not Validated

**Issue**: Proposal includes MCP protocol handshake testing but this is complex.

**From proposal**:
```python
# Send MCP initialize request
init_request = '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"1.0"}}\n'
```

**Problems**:
- This assumes stdin/stdout transport (not all servers use this)
- Doesn't account for server startup time (server might not be ready)
- No handling of malformed responses
- No validation of tools/resources schema
- select() doesn't work on Windows

**Reality**: MCP protocol testing is a project in itself.

**Questions**:
- Does mcpi need to validate MCP protocol compliance?
- Or just verify "server process starts and doesn't crash"?
- Should we use existing MCP testing tools if available?

**Recommendation**: Clarify MCP testing scope in proposal or remove Tier 3 protocol testing.
